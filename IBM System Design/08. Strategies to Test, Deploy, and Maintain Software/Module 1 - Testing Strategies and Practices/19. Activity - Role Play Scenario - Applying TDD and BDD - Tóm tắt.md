## 🎯 Mục tiêu hoạt động
1. **Phân tích yêu cầu nghiệp vụ (`REQ-202`):** Đối chiếu giữa yêu cầu chức năng thuần túy và tiêu chuẩn bảo mật ngân hàng (OWASP).
2. **Thiết lập mục tiêu kiểm thử TDD (TDD-style Test Objectives):** Xây dựng các boundary kỹ thuật rõ ràng cho đội ngũ backend.
3. **Soạn thảo kịch bản BDD (Gherkin Syntax):** Thể hiện cả luồng người dùng hợp lệ lẫn cơ chế chống dò quét tài khoản (**Anti-Enumeration**).
4. **Nhận diện khoảng trống kiểm thử & phòng chống lạm dụng (Abuse Prevention & Coverage Gaps):** Rate limiting, token lifecycle, audit logging.

---

## 🏦 Yêu cầu ban đầu & Đột phá phân tích nghiệp vụ

- **Yêu cầu gốc (`REQ-202`):**  
  *"Registered users can request a password reset via email. Unregistered users must see an error."*  
  *(Người dùng đã đăng ký có thể yêu cầu đặt lại mật khẩu qua email. Người dùng chưa đăng ký phải nhìn thấy thông báo lỗi).*

- **Phân tích rủi ro bảo mật (Security Critical Thinking):**
  - **Lỗ hổng dò quét tài khoản (User/Account Enumeration - OWASP Violation):** Nếu hệ thống hiển thị thông báo lỗi riêng biệt (ví dụ: *"Email không tồn tại"*), hacker có thể dùng bot thử hàng loạt email để biết chính xác ai có tài khoản tại ngân hàng.
  - **Quyết định kiến trúc & UX thống nhất với QA Lead:** Thay vì hiển thị lỗi riêng, hệ thống sẽ trả về **cùng một thông báo thành công chung (Generic Confirmation Message)** cho cả hai trường hợp:  
    > *"If an account exists for this email, a reset link has been sent"*  
    *(Nếu email này tồn tại trong hệ thống, một liên kết đặt lại mật khẩu đã được gửi đi).*

## 🎯 1. TDD-Style Test Objectives (Mục tiêu kiểm thử kỹ thuật)

1. **Happy Path (Người dùng hợp lệ):**
   - Xác nhận nhập email đã đăng ký hợp lệ sẽ hiển thị thông báo thành công chung.
   - Xác nhận hệ thống backend tạo mã token an toàn, dùng một lần (single-use), có thời hạn ngắn (15 phút) và kích hoạt gửi email qua SMTP/ESP.
2. **Bảo mật & Chống dò quét (Người dùng chưa đăng ký):**
   - Xác nhận nhập email chưa đăng ký hiển thị **chính xác cùng một thông báo chung**.
   - Xác nhận backend **không** tạo bất kỳ token nào trong DB và **không** dispatch email ra ngoài.
3. **Xác thực dữ liệu đầu vào (Input Validation):**
   - Xác nhận định dạng email không hợp lệ (sai cú pháp `@`, ký tự cấm, bỏ trống) bị chặn ngay bởi validation (Client & Server) với mã lỗi thích hợp.
4. **Phòng chống lạm dụng & Tấn công (Abuse Prevention & Security):**
   - Xác nhận cơ chế Rate Limiting (giới hạn tần suất gọi request theo IP và email) chặn đứng các hành vi spam/brute-force.
   - Xác nhận token tự động bị vô hiệu hóa khi: đã dùng 1 lần, hết hạn 15 phút, hoặc khi người dùng tạo yêu cầu reset mới.

## 🥒 2. Kịch bản BDD chi tiết (Gherkin Syntax)

```gherkin
Feature: Password Reset Request (REQ-202)
  As a banking customer
  I want to request a password reset via email
  So that I can securely regain access to my account

  Background:
    Given the user is on the "Forgot Password" page

  Scenario: Registered user submits valid email (Happy Path)
    Given a registered user exists with email "alice@example.com"
    When the user enters "alice@example.com" and submits the request
    Then the system displays "If an account exists for this email, a reset link has been sent"
    And a password reset email is dispatched to "alice@example.com" with a secure token valid for 15 minutes

  Scenario: Unregistered user submits email (Anti-Enumeration)
    Given no account exists with email "ghost@example.com"
    When the user enters "ghost@example.com" and submits the request
    Then the system displays "If an account exists for this email, a reset link has been sent"
    And no email is dispatched
    And no reset token is generated

  Scenario: User submits an invalid email format
    When the user enters "invalid-email-format" and submits the request
    Then the system displays an input validation error "Please enter a valid email address"
    And no password reset request is processed

  Scenario: Rate limiting blocks repeated reset attempts
    Given a user has made 5 password reset requests within 15 minutes
    When the user attempts another password reset request
    Then the system rejects the request with HTTP 429 and message "Too many requests. Please try again later"
    And no email is dispatched
```

## 🛡️ 3. Kiểm soát hệ thống & Rủi ro độ phủ (Coverage Gaps)

| Kiểm soát (Control) | Chi tiết kỹ thuật & Phòng ngừa rủi ro |
|---|---|
| **Anti-Enumeration** | Thông báo phản hồi UI và thời gian phản hồi (Response Time) phải đồng nhất giữa email tồn tại và không tồn tại, tránh cả Side-channel Timing Attack. |
| **Token Lifecycle** | Token được mã hóa ngẫu nhiên bảo mật cao (cryptographically secure), lưu trữ dưới dạng băm (hashed) trong DB, có TTL = 15 phút, dùng 1 lần duy nhất (one-time use). |
| **Rate Limiting** | Áp dụng Leaky Bucket / Token Bucket theo cả IP nguồn và tài khoản email để chống spam hộp thư người dùng và quá tải máy chủ mail. |
| **Audit Logging** | Ghi log toàn bộ các sự kiện reset password phục vụ điều tra bảo mật (không ghi log lộ token bí mật). |
