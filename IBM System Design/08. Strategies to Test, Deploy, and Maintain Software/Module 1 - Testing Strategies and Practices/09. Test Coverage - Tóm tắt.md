## 🎯 Mục tiêu bài học
- Hiểu khái niệm và tầm quan trọng của **Test Coverage**.
- Biết cách đọc và sử dụng **Test Coverage Report** (ví dụ với công cụ `coverage` trong Python) để bổ sung test case cho các dòng code chưa được thực thi.
- Hiểu lý do vì sao **100% Test Coverage vẫn có thể tồn tại Bug**, và tại sao vẫn phải tiếp tục kiểm thử.

---

## 📐 1. Test Coverage là gì?

> **Test Coverage (Độ bao phủ kiểm thử)** là tỷ lệ phần trăm giữa **số dòng code thực tế được chạy (executed)** trong quá trình test trên **tổng số dòng code có thể thực thi (executable statements)**.

$$\text{Coverage (\%)} = \frac{\text{Số dòng code được test thực thi}}{\text{Tổng số dòng code thực thi}} \times 100$$

- **Độ bao phủ cao** mang lại sự tự tin rằng phần lớn logic code đã được kích hoạt và chạy qua trong lúc kiểm thử.
- Test coverage report không chỉ chỉ ra code nào đã test, mà quan trọng hơn là **chỉ ra chính xác dòng code nào chưa từng được chạy qua (`miss`)** để bổ sung test cases.

---

## 📊 2. Phân tích Test Coverage Report (Thực hành với Python `coverage -m`)

Khi chạy lệnh đo coverage với flag `-m` (`--show-missing`), báo cáo sẽ hiển thị:

| Cột | Ý nghĩa | Ví dụ trong bài |
|-----|---------|-----------------|
| **Name** | Tên file mã nguồn được kiểm thử | `server.py` |
| **Stmts** | Tổng số câu lệnh thực thi trong file | `81` statements |
| **Miss** | Số dòng code chưa từng được chạy qua | `5` dòng (chưa rõ hành vi khi lên production) |
| **Cover** | Tỷ lệ phần trăm bao phủ hiện tại | `94%` |
| **Missing** | Danh sách số dòng cụ thể chưa được thực thi | `62, 66, 167-169` |

## 🛠️ 3. Quy trình tăng Coverage qua ví dụ thực tế

### Bước 1: Tra cứu dòng code bị "Miss"
- Xem dòng 62 trong `server.py`: Đây là hàm xử lý lỗi trả về mã lỗi HTTP **405 Method Not Allowed**.

### Bước 2: Tìm điều kiện kích hoạt dòng code đó
- Kiểm tra danh sách route hợp lệ (`flask routes`):
  - Endpoint `/accounts` chỉ hỗ trợ method `GET` và `POST`.
- Để kích hoạt lỗi **405 Method Not Allowed**, cần gọi một method không được hỗ trợ (ví dụ: `PUT`) vào `/accounts`.

### Bước 3: Viết test case bổ sung
```python
def test_method_not_allowed(self):
    # Gửi request PUT không được hỗ trợ tới endpoint /accounts
    resp = self.client.put('/accounts')
    # Assertion kiểm tra mã lỗi trả về đúng 405
    self.assertEqual(resp.status_code, 405)
```

### Bước 4: Chạy lại report và kiểm tra kết quả
- Dòng 62 biến mất khỏi danh sách `Missing`.
- Số dòng `Miss` giảm từ 5 xuống 4.
- Coverage tăng từ **94% lên 95%**.
- Tiếp tục quy trình tương tự với các dòng còn lại (`66`, `167-169`).

## ⚖️ 4. Happy Paths vs. Sad Paths

- **Happy Paths (Luồng thuận):** Dữ liệu chuẩn, các luồng thành công. Chỉ test Happy Paths **không bao giờ đạt được full test coverage**.
- **Sad Paths (Luồng nghịch/lỗi):** Các nhánh `else`, xử lý ngoại lệ `try/except`, lỗi validation dữ liệu, mã lỗi HTTP (400, 404, 405, 500...). Muốn đạt độ bao phủ cao, **bắt buộc phải test đầy đủ các Sad Paths**.

---

## ⚠️ 5. Cạm bẫy: "100% Test Coverage vẫn có thể có Bug"

> **100% Test Coverage KHÔNG đồng nghĩa với mã nguồn không có lỗi!**

- **Bản chất của 100% Coverage:** Chỉ phản ánh rằng *mọi dòng code đều đã được chạy qua ít nhất một lần với một bộ dữ liệu đầu vào nào đó*.
- **Tại sao vẫn có lỗi?**
  1. Thiếu các trường hợp biên (**Edge cases / Corner cases**).
  2. Dữ liệu đầu vào bất thường, dị thường (**Bad/Malformed data**) chưa được kiểm thử.
  3. Lỗi logic nghiệp vụ hoặc sai thứ tự xử lý trong môi trường đồng thời (race condition).
- **Lời khuyên thực tiễn:** Không dừng lại khi đạt 100% coverage. Luôn tiếp tục thử thách tính toàn vẹn của code bằng bad data, edge cases trong cả điều kiện bình thường lẫn tải nặng/bất lợi.
