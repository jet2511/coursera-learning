## 💡 Định nghĩa & Bản chất của TDD

### 1. Test dẫn dắt thiết kế (Test Drives Code Design)
- **TDD không đơn thuần là kiểm thử:** Các ca kiểm thử đơn vị (**Unit Test Cases**) chính là tài liệu đặc tả thiết kế (**Design Document**).
- **Góc nhìn Consumer-First (Người dùng API):**
  - Khi viết code trước, lập trình viên thường sa đà vào chi tiết bên trong, dẫn đến việc thêm tham số tùy tiện mà bên gọi (caller) không thể cung cấp được.
  - Viết test trước buộc lập trình viên phải đứng ở góc độ người gọi hàm: *API này cần nhận vào tham số gì? Kỳ vọng trả về kết quả gì? Cách gọi có tự nhiên và thuận tiện không?*
- **Quy tắc vàng:** *"Viết test case cho đoạn code mà bạn ước mình có sẵn (Write tests for the code you wish you had), sau đó mới viết code để test pass."*

## 🔄 Quy trình Red / Green / Refactor

Quy trình phát triển trong TDD tuân theo vòng tròn lặp lại 3 bước cơ bản:

```
      ┌────────────────────────────────────────────────────────┐
      │                                                        │
      ▼                                                        │
┌───────────┐         ┌─────────────┐         ┌──────────────┐ │
│ 🔴 RED     │ ────▶   │ 🟢 GREEN    │ ────▶   │ 🔵 REFACTOR   │ ─┘
│ Write a   │         │ Write just  │         │ Clean up &   │
│ failing   │         │ enough code │         │ improve code │
│ test case │         │ to pass     │         │ quality      │
└───────────┘         └─────────────┘         └──────────────┘
```

1. **🔴 RED (Viết test thất bại):**
   - Viết một unit test thể hiện hành vi/tính năng mới.
   - Chạy test và xác nhận test bị **Fail** (báo đỏ) vì mã nguồn thực tế chưa tồn tại.
2. **🟢 GREEN (Viết code tối thiểu để pass):**
   - Viết lượng code vừa đủ để test chuyển sang màu xanh lá.
   - Code chưa cần đẹp, chưa cần tối ưu (thậm chí có thể hardcode giá trị trả về) — mục tiêu duy nhất là thỏa mãn test case.
3. **🔵 REFACTOR (Tái cấu trúc):**
   - Dọn dẹp mã nguồn, loại bỏ trùng lặp, cải thiện hiệu năng, thay thế giá trị cố định bằng thuật toán thực tế.
   - Nhờ có bộ test bảo vệ, lập trình viên tự tin refactor mà không sợ phá vỡ logic cũ.
4. **Lặp lại:** Chuyển sang tính năng/hành vi tiếp theo.

## 🚀 Lợi ích của TDD đối với DevOps & CI/CD

| Lợi ích | Chi tiết |
|---|---|
| **Tiết kiệm thời gian & Tăng tốc độ code** | Lập trình viên code nhanh hơn và tự tin hơn vì không còn nỗi sợ "sửa chỗ này làm hỏng chỗ kia" (Regression). Test case phản hồi ngay lập tức nếu có lỗi. |
| **Đảm bảo code đúng kỳ vọng** | Bộ test định nghĩa chính xác hành vi; khi test pass tức là tính năng đã hoàn thành đúng mục tiêu (Definition of Done rõ ràng). |
| **Lưới an toàn chống Regression** | Khi sửa code hoặc thêm tính năng trong tương lai, hệ thống test tự động sẽ cảnh báo ngay nếu có lỗi phát sinh. |
| **Nền tảng bắt buộc của CI/CD** | **Không thể có CI/CD pipeline nếu thiếu automated tests.** Tự động hóa CI/CD mà không có test tự động thì chỉ tương đương với việc "đưa lỗi lên Production nhanh hơn" (*pushing bugs to production faster*). |

---

## 📌 Ghi nhớ cốt lõi
> - **TDD là Design Document:** Test case đặc tả hành vi của hàm trước khi code được viết.
> - **Red / Green / Refactor:** Viết test fail $\to$ Viết code tối thiểu để pass $\to$ Tái cấu trúc sạch đẹp.
> - **TDD là xương sống của DevOps:** Test tự động là điều kiện tiên quyết để xây dựng pipeline CI/CD tin cậy.
